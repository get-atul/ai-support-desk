I am building a production-oriented AI knowledge and support platform called **AI Support Desk**.

Please treat this as an ongoing software architecture/development project, not as a simple RAG demo.

## 1. Overall goal

I want to build a web application where users can:

1. Create multiple projects.
2. Select an active project.
3. Add knowledge/data to that project.
4. Ask questions about that project's knowledge.
5. Receive answers using RAG + an LLM.
6. Keep knowledge completely isolated between projects.

The long-term goal is an **industry-standard, extensible AI knowledge platform**, so please avoid shortcuts that would make future scaling, security, multi-tenancy, or additional data types difficult.

## 2. Knowledge ingestion requirements

A project should eventually support multiple knowledge sources, including:

* Text
* PDF
* DOC/DOCX
* Excel/CSV where appropriate
* Images
* Audio
* Video
* Web content
* Possibly URLs
* Pasted text

Audio and video should eventually go through transcription before being indexed.

Images may eventually require OCR and/or multimodal vision models.

The architecture should therefore separate:

**Source ingestion → extraction/transformation → chunking → embedding → vector storage → retrieval → LLM response**

Do not tightly couple the RAG system to only "meeting transcripts".

## 3. Future multilingual requirement

The platform should eventually support multiple languages.

The architecture should therefore not assume that all documents or questions are English.

Future capabilities may include:

* multilingual documents
* multilingual embeddings
* multilingual questions
* translation where required
* language detection
* language-aware transcription
* potentially different models for different languages

We don't need to implement all of this immediately, but the architecture should allow it without a major rewrite.

## 5. Current RAG implementation

My current RAG implementation already works.

`core/vector_store.py` currently:

* creates HuggingFace embeddings
* uses `all-MiniLM-L6-v2`
* uses Chroma
* stores the vector database in `vector_db`
* uses `RecursiveCharacterTextSplitter`
* uses chunk size 500
* uses chunk overlap 50
* retrieves the top 4 chunks using similarity search

`core/rag_engine.py` currently:

* creates an OpenAI `ChatOpenAI` instance
* uses `gpt-5-nano`
* loads the Chroma vector store
* creates a retriever
* builds an LCEL RAG chain
* formats retrieved documents
* sends context + question to the LLM
* returns a string answer

The current prompt instructs the model to answer only from the retrieved context and say:

"I could not find this information in the meeting transcript."

when the answer isn't available.

We already tested loading the existing RAG chain successfully.

## 7. Important architectural requirement: projects

The application must be project-aware.

For example:

```text
Project: Customer Support
    ├── refund-policy.pdf
    ├── support-call.mp3
    └── FAQ.docx

Project: HR
    ├── employee-policy.pdf
    └── leave-policy.docx

Project: VideturPro
    ├── legal-faq.pdf
    ├── previous-cases.docx
    └── website content
```

When the user selects `Customer Support`, the chatbot must retrieve information ONLY from the Customer Support knowledge base.

It must never accidentally retrieve information from HR or another project.

## 9. Vector database/project isolation

I initially considered:

```text
vector_db/
    project_A/
    project_B/
    project_C/
```

but I am open to a better design.

For the initial version, using Chroma collections/namespaces per project may be appropriate.

However, please think about:

* multi-tenancy
* project isolation
* metadata filtering
* scalability
* security
* indexing
* migration to a production vector database later
* whether Chroma should remain the long-term vector DB
* whether PostgreSQL + pgvector or another vector DB would be more appropriate eventually

Do not prematurely overengineer the current local development environment, but don't create an architecture that will require a complete rewrite later.
